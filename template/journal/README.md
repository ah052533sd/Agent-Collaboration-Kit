# 协作流水（Collaboration Journal）

> 跨 Agent 共享的**过程判断**，不是结论。按日期组织，append-only。
>
> 检索别名（中文 / English aliases）：协作流水、过程日志、会话流水、交接日志 / Collaboration Journal, process log, session journal, handoff log

## 为什么存在这一层

知识层按主题收敛已确认结论，任务目录按任务保存产物和证据。两者都会**过滤掉过程**——试过什么、否决了什么、为什么放弃某条路。

但多 Agent 协作恰恰需要过程：另一方要能复核你的判断，而不只是接受你的结论。用户也不应该为了让两边 context 对齐而手工粘贴分析结果。

所以本层是唯一**按时间、跨任务**的层，且**允许写半成品**：没验证的判断、被否决的想法、还没想清的方向都能进。这是它和知识层的本质区别——本层不要求证据标签，也不承担规范性。

**本层不是规范知识。** 引用本层内容时必须标明它是过程记录；要变成项目事实，仍须走知识层的证据门槛。

## 写什么

每条包含（没有的项直接省略，不要写「无」凑格式）：

- **在做什么**——本次会话的单一主目标
- **过程判断**——做了哪些判断、依据是什么，包括还不确定的
- **否决了什么**——试过或考虑过但放弃的路径，以及放弃的理由
- **发现**——过程中查证到的事实（同时该进知识层的另行处理，此处只留指针）
- **未决项**——留给下一个会话或另一方的问题
- **下一步**——接手的人该从哪一步动手。与「未决项」不同：未决项是还没解决的问题，下一步是可执行的动作。**token 快耗尽、会话可能中断、或即将换手时必写**——这是接力能不能接上的唯一依据
- **产物**——本次产出或改写的文件路径，用 `--artifact` 传，**产出了文件就必写**。写在正文里不算：正文会被注入预算截掉，产物行不会（见下「读取规则」）

## 不写什么

- 逐字对话记录（原始记录已在会话日志里，见下）
- 凭据、token、密钥、`.env` 值
- 工具调用流水、命令输出（有价值的结论写进来，过程别抄）

## 怎么写

一天一个文件：`journal/YYYY-MM-DD.md`。**两侧共用同一个写入入口**（flock 加锁，同时写不会互相截断）：

```bash
/usr/bin/python3 journal/bin/append.py --agent claude \
  --session-id "<本次会话 id>" \
  --title "<一句话标题>" \
  --doing "<单一主目标>" \
  --judgment "<关键判断及依据>" \
  --rejected "<否决的路径及理由>" \
  --finding "<查证到的事实>" \
  --open "<留给对方的问题>" \
  --next "<接手的人从哪一步继续>" \
  --artifact "<本次产出或改写的文件路径>"
```

`--session-id` 请尽量带上：`end.py` 靠它精确判断本次会话是否空转（漏传时退回比对会话起始时间）。字段可重复传入。`--artifact` 的路径不存在时只警告不阻断——可能还没落盘，也可能名字写错了，后者正是要抓的。生成的条目形如：

```markdown
## [claude] 14:30 PDT — 标题

- **在做什么：** …
- **过程判断：** …
- **否决了什么：** …
- **未决项：** …
- **产物：** `<路径>`
```

`## [agent] 会话信封 HH:MM TZ` 形式的条目由 SessionEnd hook 自动追加，压成单行，只记 HEAD、未提交改动和原始记录路径。它保证「会话发生过、原始记录在哪」可被另一方发现，**不携带语义**——语义部分必须由 Agent 在会话中自行追加，hook 代劳不了：SessionEnd 触发时会话已结束，取不到模型的总结。信封不进注入，也不算游标。

## 读取规则

会话开始时读取**比自己上次语义条目更新的条目**，不全读，也不重读自己写过的。两侧都已机械化，且共用同一份实现（只差 `--agent` 一个参数，行为不会两边漂移）：

| | Claude | Codex |
|---|---|---|
| 读取（每会话一次） | [`.claude/settings.json`](../.claude/settings.json) `SessionStart` | [`.codex/hooks.json`](../.codex/hooks.json) `SessionStart` |
| 义务提醒（每轮） | 同上，`UserPromptSubmit` 分支，约 330 字符 | 同上，`UserPromptSubmit` 分支，约 330 字符 |
| 信封（会话结束） | 同上，`SessionEnd` → [`bin/end.py`](bin/end.py) | 同上，`SessionEnd` → [`bin/end.py`](bin/end.py) |

实现：[`bin/context.py`](bin/context.py)（读取侧）、[`bin/end.py`](bin/end.py)（信封）、[`bin/append.py`](bin/append.py)（语义条目）、[`bin/peek.py`](bin/peek.py)（兜底抽取）、[`bin/_journal.py`](bin/_journal.py)（共用逻辑）。**两侧共用一份实现是硬要求**：曾经两侧各写一份，半天内漂移出四个 bug（游标把信封当语义条目导致静默漏读、注入不过滤信封、空转判定按天失效、对方写 journal 触发本方写信封）。

游标是**各自最后一条语义条目**（`[claude]` 认自己的 `[claude]` 条目，`[codex]` 认自己的），信封不算语义条目、也不进注入。因此注入量不随信封累积增长。

**会话中途的追赶：** SessionStart 只在会话开始时跑一次，长会话里对方后写的条目本来看不到。因此每轮提醒的 hook 会顺带比对一次本会话水位（`.journal-state/<agent>/<session>.seen`）：对方有新条目就直接带进来，水位随之前移，**同一条不会重复注入**；自己写的条目和信封不带。超过 2000 字符时只给标题和补读指引。这**不是轮询**——不新增任何触发点，只是让本来每轮都跑的 hook 多做一次文件比对，实测每轮仍是 40–50ms。

## 冲突规则

本层 append-only，天然低冲突：两方追加不同日期文件，或同一文件的不同时间段，几乎不会撞；同时写也有 flock 兜底。因此**本层写入不需要用户确认**。

一旦出现真正的同段落冲突，仍按 [`AGENTS.md`](../AGENTS.md) 第 3 条（并发与冲突）处理：停下，把冲突双方原文报告给用户。

## 兜底通道：原始会话记录

journal 是压缩，必然有损。以下位置保存两侧的完整原始会话记录，**实时落盘、明文可读**：

| Agent | 位置 |
|---|---|
| Claude Code | `~/.claude/projects/<项目路径转写>/<session-id>.jsonl` |
| Codex | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`（全局目录，按 `session_meta.cwd` 过滤本项目） |

**只在两种情况下读取**：journal 缺失（会话崩溃或未及时追加），或需要复核对方某个判断的原始上下文。不要例行全读——量大、噪音多，且混着被否决的路径，分不清哪句是结论。

**必须抽取，禁止全读。** 实测出现过 135 MB 的单个 Codex rollout，直接 `Read` / `cat` 一次即撑爆上下文。一律用：

```bash
/usr/bin/python3 journal/bin/peek.py --agent codex            # 对方近 24h 记录（已按本项目过滤）
/usr/bin/python3 journal/bin/peek.py --agent claude
/usr/bin/python3 journal/bin/peek.py --agent codex <jsonl 路径>
/usr/bin/python3 journal/bin/peek.py --agent codex --full     # 单条上限放宽到 100000 字符
```

它只抽 user / assistant 消息，丢掉 tool call、tool output、reasoning 和环境注入。压缩比随样本差别很大，三个实测点：135 MB → 51 KB（0.04%）、881 KB → 4.3 KB（0.5%）、449 KB → 4.8 KB（1.1%）。

这两个位置不在版本控制内，换设备即失效。跨设备场景下只有 journal 和知识层可靠。

## 成本控制

四条硬约束，保证成本不随时间漂移：

1. **游标 + 过滤信封**——只注入对方比自己上次语义条目更新的内容。实测对比：不过滤信封时单次注入 6120 字符（24 条信封 + 1 条被截断的语义），过滤后 1365 字符（0 信封 + 1 条完整语义）。
2. **注入上限**——单文件 6000 字符、最多 3 天；截断和被省略的文件都显式标注，提示 Agent 主动补读，而不是误以为看全了。**超预算按条目整条丢弃，不按字符拦腰截断**，且被丢的条目留下标题 + 产物路径。拦腰截断会把一条判断从句子中间切开，读的人分不清是没写完还是被切了；更严重的是产物路径写在正文里，一截就没了——实测一天 28 条语义条目 30876 字符，三条同主题条目 4295 字符全被压成三行标题，另一方据此**定位到了错的产物且不自知**。
3. **每轮提醒极短**——无新条目时约 330 字符（随仓库路径长度浮动，实测 326–340），只说「有关键判断就立即追加」并给出写入模板。20 轮约 6.6k 字符，比一次性全量注入还少。只有对方在你会话中途写了条目时才变长，且水位前移保证同一条不重复。模板里带 `--artifact` 是有意的：它每轮进上下文，而协议文档不进——**能靠机制提醒的不靠文档提醒**。
4. **原始记录一律走抽取**——`peek.py`，实测 0.04%–1.1%。

写入侧另有两条：

- **空转会话不写信封**——HEAD 未变、工作区干净（`journal/` 的改动不计，可能是对方刚写的）、且**本次会话**没写过语义条目时直接跳过。判定精确到会话，**不是精确到当天**：按天判断会在当天写过第一条之后失效，之后每个会话都被判成「干过活」，实测一天堆出 25 条信封对 4 条语义。
- **信封压成单行**——`HEAD x｜未提交 y｜记录 z`，路径超过 6 项折叠为「等 N 项」；记录路径校验存在性，推导不到时显式标注。

每条 journal 条目应是摘要而非全文。超过约 4000 字符就说明写细了——细节属于任务目录，结论属于知识层，此处只留判断和理由。
