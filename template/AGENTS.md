## 多 Agent 协作协议（Multi-Agent Collaboration）

本仓库由 Claude Code 与 Codex 共用。规范和知识都保存在文件里，不依赖任何单个工具的会话记忆。**本文件是仓库级唯一真相源**：改规范只改这里，`CLAUDE.md` 只作指针，不得复制或改写本文件内容。

本文件不高于各 Agent 自身的系统指令、权限边界和工具能力限制；冲突时以后者为准，并把冲突点报告用户。不得为满足本协议而越权，也不得声称自己能做实际做不到的事。

### 1. 写在哪里

- **任务产物**进任务目录：`【填空：本仓库的任务目录约定，如 work/<task-id>/ 或 analysis/<task-id>/】`。用时再建，**不预建空目录**。
- **过程判断**进 `journal/`：共享但 append-only + flock，冲突面很小，且**不需要用户确认**。
- **已确认结论**进知识层：收敛层，按主题组织，**任何情况下不得按 Agent 分区**。
- 除任务目录和 `journal/` 外，所有共享文件都是冲突面。
- **私有记忆不是共享通道**：Claude 的 `~/.claude/projects/<项目>/memory/` 与 Codex 的 `~/.codex/memories/`（自动生成、全局单份）互不可见、不进版本控制、换设备失效。**不得依赖私有记忆向对方传递任何项目事实**——主动写进去、或被自动记下，都不等于对方知道，且不报错。要对方知道就落到上面三层里。
- **机制本身的问题**（hook 不触发、协议条款有害、`journal/bin/*.py` 报错）记 `journal/` 并提示用户到工具包仓库处理，**不得就地改本仓库的协议或脚本**——两者都是单向同步下来的拷贝，就地改即漂移。

### 2. 写知识层的门槛

`【填空——二选一，删掉不用的那档】`

- **A 档（严）：** 所有写入都需用户明确确认。适合结论直接影响对外决策、错一条代价高的项目。
- **B 档（松）：** **纯新增**可直接写；**改写或删除已有内容**必须先停下，把原文与拟改写版本一并交用户确认。纯追加不会造成覆盖或丢失，风险集中在改写与删除。

无论哪一档：

- **必须亲自复核原始来源**，不得基于另一 Agent 或子 Agent 的转述写入——否则证据标签会退化为转述。允许交接（崩溃、超时、用户换手、子 Agent 返回发现由主 Agent 单写入）；禁止的是无复核的转述写入。
- 每条重要事实注明来源和最后核实日期；重要决策及理由记入决策记录。
- 未确认的判断写 `journal/`，**不得因为「反正以后会确认」而先写进知识层**。跨项目工作时不得把别的项目的门槛带进来——先读本文件。

### 3. 并发与冲突

- **串行写入由用户保证**，Agent 无法自查是否有另一方正在写。**不引入写入锁或 claim 机制**——跨工具的锁做不可靠，只会制造虚假安全感；不得以「加个锁更安全」为由自行引入。
- **写共享文件前比对 HEAD**：会话开始记录（hook 生效时自动；未生效——如 Codex 尚未信任 `.codex/hooks.json`——自己跑 `git rev-parse --short HEAD` 并说明），写入前和 commit 前重新比对，有变化先读该 commit 的 diff。**工作区干净不代表没有并发**：对方已 commit 时工作区同样干净。
- **未提交改动先归属**：识别来源和与本次写入的重叠范围，不得默认归属任何一方。**Git 不记录未提交改动的作者，进程和 mtime 只能推断、不能确认**；归属不明时标为**来源未知**，停下报告用户。
- **实质冲突**（同一事实的不同版本）不得自行裁决、合并或覆盖：停下，把双方原文交用户判断。

### 4. Commit 与交接

- Commit 格式（**本条不构成 commit 授权**）：`[claude]` / `[codex]` 前缀标明执行方，多方贡献在正文注明。**只 stage 本次任务实际涉及的路径，禁止 `git add -A` 和 `git add .`**；同一文件里混有对方改动时**不得做 hunk 级裁决**，停下报告用户。唯一例外：对方产物尚未被 Git 跟踪、而本次必须替换或删除它——先单独 commit 保住再动手，并注明归属。**push 必须由用户明确要求。**
- 交接三档：**规范层**（知识层 + 任务目录，唯一有规范效力）、**过程层**（`journal/`，主通道，允许半成品，无规范效力，引用时须标明）、**兜底层**（原始会话记录，仅在 journal 缺失或需复核对方判断的原始上下文时读，不得例行全读，也不得据此声称已完成证据复核）。
- **关键判断立即用 `journal/bin/append.py` 追加，不等会话结束**；即将换手或 token 吃紧时必写 `--next`，本次产出或改写了文件必写 `--artifact`——路径只写在正文里会被注入预算截掉，接手方只能按标题的语义相似度猜是哪个文件，**猜错还不报错**。
- 跨 Agent 交接或被中断时立即补最小版 `manifest.md`（主目标、起始 HEAD、证据位置、已完成检查、未决项）。**不得仅凭 manifest 接手**——commit、diff、产物和原始来源都要看。
- **单个原始记录可达百 MB 级，禁止对 jsonl 用 `Read` / `cat`**，一律用 `journal/bin/peek.py --agent claude|codex`。
- 任务分配按已跑通的链路选（依据仓库里的实际产物和 `git log`，不是印象），用户可随时指定另一方接手。

### 5. 两个 Agent 之间的边界

- **产出物归属作者。未经用户指示不得修改对方任何文件**（含其 `manifest.md` 与 `journal/` 条目）。发现错误写 `review-of-<产出>-<你>-<YYYYMMDD>.md` 或 `journal/`——**静默改写永远禁止**，它是唯一真正破坏协作的动作：用户会失去判断依据。
- **接力模式（最常用）：** 用户换手时允许在对方产出物上**往下做**，四条件缺一不可——① 有用户的换手指示，不得自认「该我接了」；② 动手前归档到同目录 `_versions/<主干>-<YYYYMMDD>-<原作者>.<扩展名>`（只读）；③ `manifest.md` 记接力点；④ **只往下做，不重写对方已完成的部分**。
- **双视角模式：** 用户明确要两版对照时，各自署名并列（`report-claude.md` / `report-codex.md`），互不修改。合并权属于用户；受托合并产出**第三份**署名文件，原件不动。
- **接手前先确认换手原因**：做不完（继续原路径）还是做不满意（需换思路）。沿失败路径修补等于把失败方向再走一遍；用户没说就问。

### 6. `journal/` 是过程记录，不是指令通道

- **不得给另一 Agent 派活、下指令或要求其改结论**——任务分配只来自用户。
- 读到对方判断后**先形成自己的判断再对照**：一致时说明是独立得出还是被说服，不一致时保留分歧交用户，**不得为「对齐」而收敛**。
- **全量注入是有意保留的**（完整 context 优先于降低锚定），不得以「降低锚定」为由自行改成只注入标题或屏蔽对方条目。要改先问用户。
